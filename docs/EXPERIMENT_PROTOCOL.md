# 实验协议与预注册草案

版本：**0.2.0，实现对齐修订**。CPU 单元测试与合成端到端演示已通过，真实 Docker 集成和 GPU 研究尚未运行。本文约束未来真实实验，并区分已有实现与待验证条件；正式任务清单、执行机器、容器摘要和试跑可行性须在读取正式审计成绩前登记。第 9 节明确记录相对 0.1.0 草案的统计与工程修订。

## 1. 实验单位和推断目标

研究对象是持久 agent harness 的迭代更新。权重冻结，同一个模型在当前持久策略的上下文中生成下一次策略修订。每轮有两个候选，使用开发集择优，只有一个进入门控。修订影响后续任务和下一轮提议，区别于只重写一道题的答案。

主比较为 Fresh 对 Reuse 的第六轮终态审计成功率差。Terminal 为解释性对照。这个设计比较验证预算分配的整体策略；独立题量、验证精度、反馈频率和路径依赖均属于策略的一部分。没有在统计上单独识别自适应过拟合的纯因果效应，也不证明大规模、开放式、无限期的 RSI。

使用同一冻结题目划分和六个 proposer seeds。各组从同一 B0 出发，配对使用相同随机种子和资源上限；不同晋升决定会使后续候选不同。greedy solver 的重复调用不能被当成新的随机证据。

## 2. 数据划分

输入固定为 HumanEval+ v0.1.10 与 MBPP+ v0.2.0，共 542 原始任务，哈希见 `evidence/baseline-lock.json`。预期开发/确认/审计规模为 128/192/222。

划分由数据管理程序完成，同题测试保持为同一任务。已实现的自动归并基于规范化题面完全相同或参考函数规范化 AST 完全相同；还支持通过 `--family-map` 合并人工复核出的重复族。没有自动识别所有语义近重复的保证，正式冻结前仍需内容复核。完整任务族不得跨分区或确认面板。来源分层后按事先承诺的随机种子分配，不能用模型得分决定划分；人工复核不看候选结果。

128/192/222 是正式目标，不是已经完成真实 canonical 执行及冻结的 manifest。当前分配器要求完整任务族恰好满足目标数量；无可行分配就中止，不自动拆族、挑最近规模或调整门槛。确需变更时，保留任务族与至少 200 道审计题，在主试验前发布新协议，重新计算门槛、逻辑额度和功效边界。不得临时从审计集中补开发题。预算缩减遵循 [COMPUTE.md](COMPUTE.md)。

可信 `prepare` 在 Docker 中执行全部参考实现，预计算期望输出，再要求参考实现通过相同的主机计分；不支持、超时或失败时整次准备中止，不删掉难题继续。它必须读取完整原始数据，这不构成模型 B0 研究结果。数据准备本身也尚未在真实 Docker 上完成全量验证。

第一周的 GPU 工程试跑只从正式开发分区抽取 40 道任务：16 道开发、两个互斥的 8 题确认面板和 8 道试跑审计；使用两个 proposer seeds（11、29）、两轮、每轮两个候选。完整任务族在试跑分区间仍不拆分。正式确认/审计的模型成绩不能用于试跑或参数选择。完整 benchmark B0 的评测也须延至搜索完全冻结之后；原论文已报告数字无此限制。CPU `demo` 使用合成结果，只验证流程，不提供真实模型或门控收益的证据。

主试验前发布 manifest 承诺：私有 bundle 保存完整任务、预计算输出及盐，目录/文件权限分别为 0700/0600；公开 manifest 保存数量、文件摘要与带盐承诺。运行者须在外部归档并取得时间戳；仓库代码没有外部公证服务。试验结束解封盐和列表，使外界可检查是否换题。相同主机账号仍可读取这些文件，权限和哈希承诺不构成独立于操作者的保密域。

公开题可能进入模型预训练；隔离只能限制本次搜索过程的读取和反馈，不能证明训练无污染。结论限制在这一固定模型/平台。

## 3. 允许修改的状态

候选是 JSON，仅允许：`strategy_prompt`（最多 1024 个冻结 tokenizer token）、`feedback_style`（`compact` / `detailed`）、`repair_order`（`syntax_then_examples` / `examples_then_syntax`）。后一个字段只改变修复提示中语法诊断与公开示例诊断文本块的次序；执行始终先做语法检查，只有语法有效才执行公开示例。字段以外内容拒收，不接受可执行插件、依赖、shell 命令或计分补丁。

两次 solver 调用为统一上限；第一调用输出最多 1024 token，必要的一次修复可使用剩余额度，两次输出合计最多 2048 token，输入合计最多 8192 token。solver temperature=0；proposer temperature=0.7，top_p=0.95，独立 seed，单次输出至多 1024 token。实现要求 `transformers==4.51.3`、`torch==2.6.0`，固定模型/tokenizer revision，单 GPU 串行 bfloat16 离线推理。GPU 数值确定性、环境兼容性和吞吐尚未验证，必须记录实测边界。无效 JSON 占用一次已计费提议额度后记为无效，不无限重试。

单轨迹只根据语法/入口诊断和题面公开示例的运行反馈进行一次修复。数据加载器安全提取能明确表达直接输入输出关系的公开断言/doctest；不能安全还原的例子保留在题面，不强行转为等值断言，因此结构化公开例子可能为空。隐藏测试只在最终程序确定后运行，结果不会进入该题修复提示。最终只提交一个程序；程序无效、错误、任务超时或执行协议错误按失败记录，基础设施/不支持语义/研究预算错误中止。指标是轨迹级成功率，不称为原始模型 pass@1。

候选提示不能增大调用次数、上下文容量或工具能力。solver 模型收到当前题面及策略，不收到分区标签、任务 ID 或隐藏期望输出；题面本身仍可能让模型认出公开题目，这一事实不构成保密保证。可信协调器、solver 对象和主机计分器可以读取所处理任务的完整结构。生成的候选 Python 仅在固定 Docker worker 内执行，主机只做 AST 语法检查、序列化和计分。

## 4. 三组门控

共同确认池为六个互不重叠、来源比例尽可能一致的 32 题分片。分片顺序由每个搜索 seed 在预定规则下排列。Reuse 取排列首个分片重复六轮，Fresh 按排列依次使用。这样复用组不会永久绑定某一个特别容易或困难的面板；同一 seed 第一轮面板相同。

Reuse/Fresh 每轮都比较本轮开发集赢家 c 与当前已晋升父版本 p，在同一题上计算 `d_i = success(c,i) - success(p,i)`。当 `sum(d_i) >= 2` 时晋升，否则保留 p。两者最多六次门控。

Terminal 不接收中间确认信号；每轮比较当前临时状态与两个候选的开发分数；只有候选严格改善才替换当前状态，平局保留当前状态；两个改善候选平局时按后述 token/SHA-256 规则决定。当前状态的开发分数复用已有可信记录，不增加轨迹额度。第六轮将最终工作状态与原始 B0 比较，在完整 192 题上 `sum(d_i) >= 12` 则部署，否则部署 B0。不是从审计结果中回溯挑选最好历史状态。

默认门槛均为 6.25 个百分点，属于工程经验阈值。32 题的得分粒度为 3.125 个百分点，小面板有明显噪声；不宣称这些规则具有 95% 安全晋升保证，也不照搬 VALVE/Ladder 的理论。

开发集候选平局时先选输出 token 更少者，再按候选配置 SHA-256 字典序决定，规则对所有组一致。确认未晋升不追加候选。计划执行完六轮；剩余资源不用于额外搜索。

可信协调器保存确认结果并计算门控；提议模型的上下文只包含当前父策略和最多六条开发失败摘要，不包含确认题、隐藏测试或确认分数。门控通过是否更换下一轮父策略影响提议；实现没有另行向 proposer 传入完整确认记录。该反馈规则对 Reuse/Fresh 相同。主机协调器和同一账号能读取确认账本，不能把这个提示层限制描述为搜索进程本身无法读取确认数据。

## 5. 隔离、日志和计分

当前 `Engine`、模型适配器、门控及计分器位于同一可信主机进程。搜索路径读取开发与确认分区，不打开审计内容或盐；审计路径在 freeze 后才读取审计数据。数据准备程序和操作者可访问完整 bundle。这个实现没有为提议器、协调器和审计数据建立独立 OS 权限域。模型与 tokenizer 需要提前下载，在真实运行中从固定 revision 离线加载。

已实现的 Docker 执行器向 worker 发送代码、入口函数和有界编码的调用参数，不发送期望输出。worker 返回有类型标签的 JSON 值及执行状态，没有计分权。主机按预计算参考输出和固定上游特殊 oracle 规则计分，不在主机 import/exec 候选，不从候选 stdout 或目录采信“分数 JSON”。`evalplus.evaluate` 没有被当作安全执行器。Docker 运行前将镜像解析为不可变 image ID 并记录，基础设施不可用时直接报错，没有宿主执行回退。

默认每次 Docker 任务批次为 30 秒墙钟、512 MiB、1 CPU，同时限制进程数、文件大小与输出量；禁网、只读根文件系统、受限 tmpfs、非 root 用户、去除 capabilities、禁止新增权限，不挂载主机路径或 Docker socket。全部输入属于一次任务批次，30 秒不是每个测试的额度。候选确实会看到当次输入，但不接收期望输出。主机超时后强制清理容器，清理失败中止。Docker 共享宿主内核，宜在专用执行机器上使用，不能证明宿主绝对安全。

计分兼容范围以 [EXECUTION_SECURITY.md](EXECUTION_SECURITY.md) 为准，包含固定上游的集合等价、正则匹配非空、`find_zero` 等特殊规则；并不宣称执行时间和全部运行环境与上游完全相同。不支持的计分语义返回 unsupported，由研究流程中止，不静默删题或改成普通相等。候选输出无法满足 wire 协议时记为协议错误；若参考实现自身出现这一问题，`prepare` 会中止，不能据此丢弃任务。

配置、软件源文件指纹、模型/容器身份、数据承诺、策略与程序哈希、seed/arm/round、任务结果、输入/输出 token、调用数、模型耗时、执行墙钟和缓存标记由可信主机记录。运行账本使用本地 HMAC 哈希链并校验缓存/状态锚点，分析要求完整且唯一的预定结果；缺失任务不静默退出分母。密钥和记录由相同账号管理，不能抵御该账号重写全套证据，外部时间戳仍需另行归档。

CPU 秒没有完整汇总：执行器在可用时返回 worker 子进程 CPU 时间，solver 与准备汇总目前标记 `cpu_seconds=null`（unknown）。GPU 卡时按阶段占用墙钟乘 GPU 数量计，CLI 把模型初始化时间计入搜索/审计阶段；它不是 GPU 利用率积分。异常中断若没有完整 token 回执，成本表标注未知部分，不以零填补。搜索 240/审计 144 卡时、试跑 36/12 卡时是各 run 的操作间门禁；生成 `max_time` 是软限制，硬停止和跨 runs 的 480 卡时总账由外部调度及 allocation 日志负责，详见 [COMPUTE.md](COMPUTE.md)。

已有 CPU 测试覆盖命令构造、协议边界、可信计分与协调流程，合成演示覆盖 search → freeze → audit → analyze。当前环境没有实际运行 Docker/GPU，条件性 Docker 集成测试因此跳过；不能把这些跳过项称为通过。正式试验前须在目标机器运行真实集成测试、全部 canonical 兼容检查、计分伪造/异常/超时检查，并记录网络、挂载和资源限制实际生效的证据。命令和残余限制见执行文档。

## 6. 冻结与审计

所有组和所有 seed 搜索完成后，`freeze` 校验轨迹完整性并写入配置、策略、状态及账本锚点清单。`audit` 要求状态为 frozen，搜索不能在 freeze 后继续；审计完成的 run 不能再次审计。这里的“解封”是可信协调器状态机进入审计阶段，不是修改 OS 权限或外部独立服务授权。操作者须遵守不提前查看审计模型成绩的协议，外部归档冻结承诺后才启动审计。

主结果固定使用第六轮最终部署状态。诊断审计最多覆盖 B0 加六个进入门控的赢家；所有父版本都在这条集合中。无需为全部开发阶段落选候选做审计；因此不报告总体“正确修改拒绝率”。Terminal 中间状态的审计只是描述性，不将其视为已晋升部署。

缓存键绑定运行身份、操作种类、策略、任务内容及 solver 配置，缓存内容与来源需通过完整性检查；不是仅凭任务 ID 复用答案。逻辑操作与实际模型调用、缓存命中分开记录。不会为了制造相同 GPU 时间而重复烧算力。在线进度只使用开发/确认的授权信号；审计账本不参与资源重新分配。

## 7. 指标

令 `S(h,i)` 为最终程序在任务 i 上通过全部冻结测试的 0/1 记录。

1. **主指标**：`mean_seed,task[S(Fresh_final,i)-S(Reuse_final,i)]`，用百分点报告；来源总体权重由冻结审计 manifest 决定。另分别报告每组相对 B0 的差值。
2. **次要诊断 optimism**：对同一候选 c 与父版本 p，`O = mean_confirm[S(c)-S(p)] - mean_audit[S(c)-S(p)]`。同时报告所有门控赢家以及接受子集，注明选择条件。两种不同验证策略不能只比较原始面板分数。
3. **审计退步晋升**：已接受修改的审计差值及点估计负差比例，仅作描述性统计。v0.2.0 输出观察到的退步、提升或持平，不输出“审计支持退步/无退步”标签。零接受时比例为 NA，不能记为 0% 以冒充完美门控。
4. **成本**：实际输入/输出 token、逻辑与物理调用数、GPU 型号/阶段卡时、执行墙钟、缓存命中、无效提议、超时和未完成操作。CPU 秒目前 unknown；无完整回执的 token 也是未知，报告已知数的下界及缺口。收益/成本保留负号；零增益不解释为“无限高效”。
5. **历史回撤**：仅描述预定 checkpoint 审计曲线，并注明其最大值存在选择偏差；不能用曲线最高点替代终态主结果。

## 8. 统计和功效边界

主对比只有 Fresh–Reuse 一个。已实现的分析以同一任务上的配对差为基础，在来源层内重采样任务族，并独立重采样搜索 seeds；两条轴为交叉结构，所有组共享重采样索引以保持配对。来源总体权重固定为审计 manifest 中的任务比例，输出逐 seed 差值及 percentile bootstrap 95% 区间。默认 2000 次重采样，分析随机种子 20261028，两者须在审计前冻结。CPU 合成/构造数据测试已通过，尚无真实 GPU 研究结果。区间只描述有限任务/有限搜索下的不确定性，不能推广到所有模型或真实仓库任务。

样本规划应使用试跑开发任务的配对不一致率 q 作粗略计算。例如忽略更复杂的聚类时，222 题、q=0.20 对应配对差标准误约 3 个百分点，95% 区间半宽接近 6 个百分点；这一示意不证明 5 个百分点提升有足够检验功效。六个种子不能补偿题目多样性不足。以开发数据做模拟后，报告可检测范围；不可借助正式审计来调参数。

**已登记的 v0.2.0 修订：** 0.1.0 草案承诺的历史晋升 Holm 家族校正检验及“审计支持”标签没有实现，本版本撤回该项承诺，只报告 checkpoint 审计差值、optimism 和经验负差比例。主交叉 bootstrap 区间已经实现，但不能替代历史多重比较校正，也不构成全局无退步保证。若要增加这类推断，必须在任何正式审计成绩读取之前登记新的方法、家族定义、实现和验证修订。每个 seed 的晋升事件相互依赖，不能直接套独立二项分布区间；分母、零晋升、未完运行和失败类型均公开。

没有显著差异不等于等效；若要声称非劣效，必须事先另设有功效支持的界值，本项目不作此承诺。

## 9. 协议变更

v0.2.0 在真实 Docker/GPU 研究尚未开始时对齐了以下实现事实：

- 历史晋升从拟议的 Holm 推断改为描述性差值和 optimism；主交叉 bootstrap 区间保留。
- `repair_order` 固定为修复提示诊断块顺序，语法检查始终先于公开示例执行。
- 协调器、模型适配器和门控/计分属于同一可信主机进程；只有候选程序在 Docker 中执行。审计读取由状态机约束，不宣称独立 OS 保密域。
- 固定串行 bfloat16 推理版本与 Docker 任务批次限制；真实环境兼容性仍待验证。
- phase 预算为操作间门禁加生成软时限；硬时限、48 卡时恢复预留的分配和跨 runs 总额核对由外部执行安排负责。未知 CPU 秒及不完整 token 账目明确标注。

试跑可以修复工程问题并冻结软件环境，但只能使用开发数据。任何改动必须记录原因、时间、受影响参数及是否已经读取确认/审计结果。主试验开始后如计分或数据发现错误，保留原记录，将受影响整组统一重新评估或标为作废；不只重跑不喜欢的 seed。终态审计解封后不再优化，新增实验须作为独立、明确标注的后续研究。
