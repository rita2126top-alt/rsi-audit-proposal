# 算力预算与可行性关卡

实现版本：**0.2.0**。CPU 测试与合成演示已运行；真实 Docker 集成、GPU 模型加载、吞吐测量和完整研究均未运行。下面的数额为申请和执行计划，没有任何实测 GPU 成绩。

## 申请数额

卡型：**A100 80GB，优先单卡**。试跑：**48 GPU 卡时，7 天内**。完整：**480 GPU 卡时，28 天内，包含前述试跑**。不是 48+480，也不是已获批的额度。

卡时为 GPU 数量乘实际占用小时。真实后端当前只使用一张 GPU，按阶段墙钟计费；模型加载、等待 CPU 执行或调度的占用时间也属于该阶段，而不是只累计 GPU 核心计算时间。CPU 数据准备另记墙钟与任务数，不折成 GPU 研究成果。硬件替换需重新记录吞吐和预算，不把不同型号卡时当作等价性能。

## 任务量上界

下述计数是正式主试验的未缓存上限，不包含试跑与故障恢复重试；后两项仍需从 480 卡时总预算中支出。

采用预期 128/192/222 划分、3 组、6 个搜索种子、6 轮、每轮 2 候选。每条轨迹包含最多两次 solver 调用，不能把轨迹数与 API 调用数混为一谈。

| 每组每 seed 的阶段 | 公式 | 任务轨迹 |
| --- | --- | ---: |
| 初始策略开发评估 | 128 | 128 |
| 六轮候选开发评估 | 6 × 2 × 128 | 1,536 |
| 验证：候选与父版本均计费 | 6 × 32 × 2，或 192 × 2 | 384 |
| 初始版本 + 六轮赢家审计 | 7 × 222 | 1,554 |
| 每组每 seed 合计 | | 3,602 |
| 三组、六 seed 合计 | 3,602 × 3 × 6 | **64,836** |

另有 `3 × 6 × 6 × 2 = 216` 次候选提议，每次最多 1024 输出 token。solver 每条轨迹输出合计上限 2048 token，因此未缓存保守上限为 132,784,128 输出 token；输入上限 8192 token/轨迹，相应逻辑上限 531,136,512 输入 token。计数不是实际消耗预测，也不含失败重试预算；任何重试必须从资源余量中扣除并记录。

审计集合无需包含全部 12 个开发候选；B0 和六个进入门控/终态链的赢家足以评估晋升与父版本。精确缓存可降低重复 B0、重复父版本和未变化 checkpoint 的成本。上表为了避免漏算未扣缓存；实际执行不应主动制造无用重复。

## 分阶段预留

| 阶段 | A100 卡时计划 |
| --- | ---: |
| 最小试跑、吞吐测量、兼容与完整性检查 | 48 |
| 正式提议、开发评估和门控 | 240 |
| 冻结后的终态与历史审计 | 144 |
| 必要复核、故障恢复和余量 | 48 |
| 合计 | **480** |

试跑 48 卡时具体分配为搜索 36、试跑审计 12。试跑使用正式开发分区内部的 40 道任务、两个 seeds、两轮；这和正式三组/六种子/六轮的任务上界分开记录。正式运行配置中的 phase 额度为搜索 240、审计 144 卡时；48 卡时恢复预留不会自动加到任何一阶段，也不会在某个 run 超时后自动放行。

这些是分配计划，不是测得的运行耗时。当前后端是 `transformers==4.51.3`、`torch==2.6.0` 的离线、固定 revision、串行 bfloat16 生成，没有已实现的 batch 调度或实测加速比。试跑需测输入预填充、输出解码、不同题型、两次调用比例、容器启动和 CPU 测试尾延迟。若新增 batching，须另行登记实现修订、重新核验确定性与预算。不能只用显存够放 7B 或理想 token/s 断言可以完成。

## 已实现的计费与限时边界

`Engine` 在每个 run 内累计搜索、审计两个 phase 的 GPU 占用卡时，开始或恢复操作前检查剩余量；正式额度为 240/144，试跑为 36/12。CLI 将 Docker/模型初始化耗时传入该次 phase 起始计时，所以成功进入命令的模型加载也计费。模型调用前还检查剩余时间，并把它传给 Transformers 的软 `max_time`。超过阶段余量会中止研究，不能把未完成任务当作模型答错再生成完整结果表。

这些检查发生在操作边界，`max_time` 也不能强制抢占一个停滞的 GPU 算子；阶段可能因正在运行的操作超过额度。候选执行另有 Docker 30 秒任务批次墙钟超时及强制清理，但这不等于 GPU 全项目硬限额。**实际硬停止需由外部作业调度器或资源配额实施**，并为停止和清理保留余量。进程崩溃、初始化失败或其他未完整写入账本的占用要从外部记录补账，不能当成免费运行。

运行账本记录成功及可捕获失败阶段的占用时间、缓存命中、已知模型 token 和执行墙钟。返回前崩溃的模型调用可能没有完整 token 回执，分析会标出缺口；已知 token 合计此时是下界。CPU 秒没有完整汇总，`cpu_seconds=null` 表示 unknown。`prepare` 单独保存 `wall_seconds`、执行墙钟、参考任务数与 `gpu_hours=0`，其 `cpu_seconds` 也为 unknown；不能从墙钟自动推算 CPU 秒。

模型/策略/任务/配置完全匹配且通过完整性核验的缓存可以减少物理调用，逻辑额度仍按操作记录。多个 seeds 和 arms 在当前实现中串行运行；不能以未实现的并发或缓存命中率作为预算已经可行的依据。

## 跨运行总额核对

当前代码不负责跨试跑、正式 run 和恢复 run 的全项目额度分配。开始每个 run 前，运行者须登记 allocation，再把内部 phase 账本和外部作业/提供方用量核对，使全部支出共同不超过申请的 480 卡时。至少记录 allocation ID、用途、run ID、GPU 型号/数量、分配上限、开始/结束时间、实际卡时、phase 账本锚点及外部用量凭据；失败、重启、重新加载和空闲占用也要归属。

48 卡时恢复预留只能在明确登记用途、额度及对实验结论的影响后分配。已有 run 的配置与来源指纹被冻结，不能为了继续运行而静默调高预算、删除账本或创建一个不计入总额的新 run。恢复或复核必须保留中断记录，使用明确标识的分配和必要的协议修订。这里规定的是执行责任与记录格式，不宣称仓库已经包含自动 allocation 管理器。

## 7 天试跑验收

1. 只使用正式开发分区内部的 16 道开发、两个 8 题确认面板和 8 道试跑审计，完成三种策略、两个 seeds 各两轮的端到端闭环；不读取正式确认/审计的模型成绩。
2. 证明候选改变会影响开发行为，量化变化幅度；不要求出现正提升。若所有候选等价，报告动作空间缺乏实验信号。
3. 在专用执行机器完成真实 Docker 集成与全量参考实现兼容检查，验证计分来源、失败分母、挂载/网络/资源限制和伪造 stdout 的处理；CPU 命令构造测试和被跳过的集成测试不能代替这些证据。
4. 生成实际成本报告，以分阶段平均值及保守尾部余量外推完整工作量；报告估算区间。
5. 在未查看正式确认/审计模型成绩的条件下冻结模型/环境、划分承诺、动作空间、阈值、种子、统计程序和资源计费规则。可信协调器有确认读取能力，操作者可读取私有 bundle；不把协议约束表述为已实现的独立 OS 权限隔离。

## 预先规定的缩减与停止

- 三组方案预计超出 480 卡时：先删除解释性的 Terminal 组，保留 Fresh/Reuse 的六种子六轮主比较、终态和对应晋升诊断。两组未缓存逻辑上界是 43,224 轨迹；重新给出成本估计并在正式试验前登记。
- 主比较仍超预算、数据隔离不成立、动作空间没有可测变化或计分可伪造：停止完整研究，公开试跑失败报告，交由资助方复议。
- 不因某 seed 成绩不好而停止或重抽；不使用审计成绩选择分支、模型、阈值或保留组别。
- 内部阶段余量耗尽时停止新增操作；外部调度器负责实际硬停止，并通过 allocation 记录维持全项目 480 卡时上限。保留未完成记录，明确不能作出的推断；基础设施错误、预算中止与模型错误分别记录。

“相同资源上限”不等于“相同实际成本”。报告收益与成本时保留省下的算力，绝不为匹配消耗空跑。
